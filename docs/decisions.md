# Entscheidungen

Mit dem Benutzer festgelegte Entscheidungen. Sie gehen dem Implementierungsplan [NETEX_EXPLORER_IMPLEMENTATION_PLAN.md](../NETEX_EXPLORER_IMPLEMENTATION_PLAN.md) vor, solange dieser nicht überarbeitet ist.

## Festgelegt

| Datum | Thema | Entscheidung |
|---|---|---|
| 30.10.2026 | Umfang Profile | Nur Schweizer NeTEx-Definitionen. Andere europäische Profile (Nordic, EPIP, FR, DE …) sind kein Thema; keine Adapter dafür. |
| 30.10.2026 | Mehrere CH-Versionen | Mehrere CH-Guide-Versionen parallel über versionierte Adapter, inklusive Guides in Entwicklung. Ein generischer Explorer (ohne fachliche Deutung) bleibt als Rückfallebene. |
| 30.10.2026 | Erste Zielversion | Neueste Version des CH-Profils 2.0 (Entwurf, NeTEx 2.1), Branch `next` des Guide-Repos, abgebildet mit den dort bereitgestellten Dateien (Beispiele, Templates, Schematron, XSD). Details: [research/guide-2.0.md](research/guide-2.0.md). |
| 30.10.2026 | Guide-Dateien beziehen | Nicht ins Projekt kopieren. Ein Skript lädt sie von GitHub auf einem festen Commit (Commit-Archiv; kein Git nötig, damit auch unter Windows). Das XSD-Submodul ist im Archiv **nicht** enthalten und wird separat von NeTEx-CEN auf dem im Guide gepinnten Commit geladen (Stand `b7ac158`: `xsd` → `73b337e`). Ein Commit-Wechsel ist ein bewusster Schritt mit Testlauf (siehe „Guide-Update“); die UI zeigt den Stand. Ablage: Verweis in `netexRealisationGuideSwitzerland.lock.json` (versioniert), Dateien in `../netexRealisationGuideSwitzerland/<commit>/` (nicht versioniert, ausserhalb des Projekts). |
| 30.10.2026 | Guide-Update | Fester Stand bleibt (in `netexRealisationGuideSwitzerland.lock.json`). Ein Update wird nicht automatisch geholt, muss aber **einfach** sein: **ein Befehl** (`scripts/update-guide.sh` / `.ps1`), der (1) den neuesten Commit von `next` und den zugehörigen XSD-Commit ermittelt, (2) die Dateien in `../netexRealisationGuideSwitzerland/<commit>/` lädt, (3) einen Bericht über geänderte Guide-Dateien zeigt (neu, geändert, entfernt; Beispiele, Templates, Schematron, XSD), (4) die Tests gegen den neuen Stand ausführt und (5) bei grünen Tests den Lock auf den neuen Commit setzt. Bei roten Tests bleibt der alte Stand aktiv, der Bericht zeigt die Ursache. Eine Schaltfläche in der lokalen Oberfläche ist optional und später möglich. |
| 30.10.2026 | Kennzeichnung Entwurf | Entwurfs-Adapter in der UI als „in Entwicklung“ mit Guide-Commit anzeigen. Prüfungen gegen Entwürfe nie als „gültig“, sondern als „geprüft gegen Entwurf <Commit>“. |
| 30.10.2026 | Grosse Lieferungen zurückgestellt | Zuerst nur die kleinen 2.0-Dateien des Guide-Repos. Die 1.10-Lieferung `../netex-files/` (12 GB) und grosse Lieferungen generell kommen später. Die Entscheide zu Import und Index-Umfang unten gelten erst ab dann. Bis dahin bleibt die Architektur so, dass grosse Mengen später möglich sind (Streaming, kein vollständiges Laden), wird aber nicht darauf optimiert oder damit getestet. |
| 30.10.2026 | Import *(ab grossen Lieferungen)* | Primär aus einem konfigurierten, freigegebenen lokalen Ordner bzw. ZIP-Pfad. Browser-Upload nur zusätzlich für kleine Dateien. |
| 30.10.2026 | Umfang des Index *(ab grossen Lieferungen)* | Ganze Lieferung indexieren (leichtgewichtiger Index); Details bei Bedarf aus der Originaldatei lesen. |
| 30.10.2026 | Plattformen | macOS **und** Windows: `start.sh` und `start.ps1`; Pfade, Dateisperren und Encodings auf beiden testen. |
| 30.10.2026 | Stack (aus Plan bestätigt, angepasst durch die Entscheide unten) | React + TypeScript + Vite, Cytoscape.js, CodeMirror 6, Python-Kern (lokal unter FastAPI, im Browser unter Pyodide), SQLite, Importjob als Hintergrundprozess (kein Celery/Redis), pytest/Vitest/Playwright. |
| 30.10.2026 | XML-Parser | **pyexpat** (Python-Standardbibliothek) für das Einlesen und Indexieren: exakte Position je Element (Byte, Zeile, Spalte). **lxml** nur für XSD- und Schematron-Prüfung. Begründung: Die Position in der Datei ist Kern der Herkunftsanzeige; ein späterer Parserwechsel würde Index und Tests betreffen. Mehraufwand: eigene Verschachtelungs- und Namespace-Behandlung. |
| 30.10.2026 | XML-Pfad im Index | Pfadform (ohne Positionsnummern) einmal in einer Pfad-Tabelle speichern; jedes Objekt verweist darauf und speichert seine Position (Datei, Byte-Offset, Zeile, Spalte) sowie den Frame. Den vollständigen Pfad mit Positionsnummern (z. B. `ServiceJourney[3]`) beim Anzeigen berechnen. Keine XPath-Zeichenkette pro Objekt. |
| 30.10.2026 | Betriebsformen | **Lokal** (wie im Plan) **plus einfachere Webversion als statische Seite**. In der Webversion findet die Verarbeitung vollständig im Browser statt (Python über **Pyodide**; pyexpat und lxml 6.1.3 dort verfügbar). Kein Server, kein Upload; Dateien verlassen den Rechner des Nutzers nicht. Zielgruppe der Webversion: Guide-Dateien und kleinere Lieferungen; grosse Lieferungen nur lokal. Folge: Der Kern (Einlesen, Index, Referenzen, Projektion, Herkunft) wird als reines Python-Paket ohne Server-Abhängigkeiten gebaut, das unter FastAPI und unter Pyodide läuft; die Oberfläche greift über eine austauschbare Datenschicht zu (HTTP lokal, direkter Aufruf im Browser). Keine gehostete Server-Variante. |
| 30.10.2026 | XML-Anzeige | **CodeMirror 6** statt Monaco: schreibgeschützte Ausschnitte mit exakter Bereichsmarkierung. Begründung: leicht und einfach einzubinden, wichtig für die Webversion (Download-Grösse), gleiche Komponente lokal und im Browser. |
| 30.10.2026 | Veröffentlichung Webversion | Zielgruppe und Ort noch offen, wird später entschieden. Die Webversion wird so gebaut, dass sie als reine statische Dateien überall läuft: relative Pfade, keine serverseitige Logik, keine Annahme über Domain oder Unterpfad (z. B. funktioniert sowohl unter `/` als auch unter `/netex-ch-explorer/`). |
| 30.10.2026 | Guide-Dateien in der Webversion | **Mit der Webversion ausliefern:** Der Build lädt die Guide-Dateien und die XSD auf dem festen Commit (gleiches Skript wie lokal) und packt sie in die statische Seite. Funktioniert ohne Internet und ohne GitHub-Abhängigkeit zur Laufzeit. **Auflage:** Das Guide-Repo nennt keine Lizenz. Vor einer Veröffentlichung, die über einen privaten Kreis hinausgeht, die Weiterverteilung klären (Kontakt laut Repo: info.fachbus@sbb.ch). Die XSD von NeTEx-CEN hat eine eigene Lizenz, ebenfalls prüfen. Nutzer können zusätzlich eigene Dateien öffnen. |
| 30.10.2026 | Speicher in der Webversion | Index (SQLite unter Pyodide) **nur im Arbeitsspeicher** für die laufende Sitzung; beim Neuladen werden die Dateien neu eingelesen. Keine Daten bleiben im Browser liegen. Dauerhafte Speicherung (OPFS/IndexedDB) ist später nachrüstbar, ohne den Kern zu ändern. |
| 30.10.2026 | Ordnerstruktur | Klare Trennung von eigenem Code und fremdem Inhalt auf oberster Ebene (Vorschlag des Benutzers):<br>`NeTEx-Viewer/` = Sammelordner, nicht versioniert<br>`├── netexRealisationGuideSwitzerland/<commit>/` = Guide-Dateien + XSD, nur durch `update-guide` befüllt, nie von Hand ändern<br>`├── netex-files/` = Lieferdaten<br>`└── netex-ch-explorer/` = eigenes Projekt und eigenes Git-Repository: `CLAUDE.md`, `README.md`, Plan, `netexRealisationGuideSwitzerland.lock.json`, `app/` (`core/`, `server/`, `frontend/`), `scripts/`, `fixtures/`, `docs/`.<br>Der Pfad zu `netexRealisationGuideSwitzerland` und `netex-files` ist konfigurierbar, Standard `../netexRealisationGuideSwitzerland` bzw. `../netex-files`; `update-guide` legt den Guide-Ordner bei Bedarf an. Projektname `netex-ch-explorer` (Umbenennung von `netex-explorer` am 30.10.2026). Ersetzt die Struktur `netex-explorer-ch/` aus Plan-Abschnitt 12. |
| 30.10.2026 | Zeiten in der Fahrtansicht | Darstellung wie ein gewohnter Fahrplan: pro Halt **Ankunft** und **Abfahrt** (erster Halt nur Abfahrt, letzter nur Ankunft); keine Dauern in der Hauptansicht. Zeiten, die nicht direkt in der Datei stehen (CH 2.0: `DepartureTime` + `RunTime`/`WaitTime` aus `TimeDemandType`), tragen eine dezente Markierung „berechnet“. Ein Klick zeigt in der Herkunftsanzeige die Rechenkette, jeder Summand mit eigener Quelle (Objekt, Datei, Position) und anklickbar. Fehlt ein Summand oder ist er nicht auflösbar: „nicht berechenbar“ mit Begründung statt einer Uhrzeit. Tageswechsel nach Mitternacht kennzeichnen (z. B. „+1“). |
| 30.10.2026 | Fahrten über Mitternacht | Umsetzung der Guide-Regeln (Details und Quellen: [research/guide-2.0.md](research/guide-2.0.md#fahrten-über-mitternacht)): Betriebstag aus `AvailabilityCondition` im Kopf der Fahrtansicht anzeigen. Jede Zeit zeigt ihre Verschiebung zum Betriebstag („+1“, „+2“, „−1“). Diese ist **ausdrücklich** (`DepartureDayOffset`, `Start`/`EndTimeDayOffset` mit Quelle; fehlendes `DepartureDayOffset` = 0, als Standardwert gekennzeichnet) oder **berechnet** (Aufsummieren von `DepartureTime` + `RunTime`/`WaitTime`, mit Rechenkette). Widersprüche (z. B. berechnete Zeiten vs. `JourneyPart`-Zeiten) als Diagnose. Fahrten in Nächten der Zeitumstellung: Hinweis, dass die Dauer bei Ortszeit ohne Zone nicht eindeutig ist; nichts stillschweigend korrigieren. Beispiele 15 und 21 als Testfälle. |
| 30.10.2026 | Alle Guide-Beispiele ladbar | **Verbindliche Anforderung:** Das Tool listet alle Dateien in `src/examples/` des aktuellen Guide-Stands (Titel aus `src/examples/README.md`) und lädt jede einzeln. Angezeigt werden die Daten jeder Datei: Fahrtansicht, wo Fahrten vorhanden sind, sonst Objekt-Explorer (z. B. 16 `SITE_OFFER`, 17 `INTERCHANGE`). Ein automatischer Test lädt jedes Beispiel; Fehler erzeugen Diagnosen statt Abstürze. Neue Beispiele nach einem Guide-Update erscheinen automatisch. |
| 30.10.2026 | Fehler in Guide-Dateien | Nicht an den Guide melden. Das Tool zeigt sie an und bleibt robust: fehlerhafte Dateien werden so weit wie möglich geladen und angezeigt, Fehler erscheinen als Diagnose mit Verweis auf die Stelle. |
| 30.10.2026 | Validierung mit Erklärung | Validierungsfunktion (Plan-Phase 4), Umfang nach Aufwandsprüfung:<br>(1) Fehler aus XSD-Prüfung (lxml) und Guide-Schematron mit Datei, Zeile, Spalte und Markierung im XML.<br>(2) Verständliche deutsche Erklärung für die häufigen Fehlerarten (unerwartetes Element, fehlendes Pflichtelement, ungültiger Wert/Aufzählung, falsches Format); seltene Arten im Originaltext.<br>(3) Korrekturvorschlag aus der XSD-Meldung („Expected is …“) plus passendes Guide-Template `src/templates/<Element>.xml`.<br>(4) Link auf das Guide-Kapitel über `src/A5_annex_index.md`, und zwar auf GitHub im **exakt verwendeten Commit** (nicht auf die veröffentlichte Seite, die einen anderen Stand zeigen kann).<br>Nicht im Umfang: automatisch korrigierte Dateien; das Tool ändert nie Dateien. Risiko: XSD-Laden in der Webversion (Pyodide); falls zu langsam/speicherintensiv, dort eingeschränkt anbieten und das dokumentieren. Erste Testfälle: Beispiel 05 Zeile 399, Beispiel 16 Zeile 64. |
| 30.10.2026 | Anzeige von Codes und Stammdaten | **Keine erfundenen Angaben.** Rangfolge:<br>(1) Steht ein Text in der NeTEx-Datei (z. B. `TypeOfProductCategory/Name`, `Notice/Text`), wird er mit Herkunft angezeigt.<br>(2) Enthält die Datei nur einen Code, wird **immer der gesendete Code** angezeigt, dazu die Bedeutung aus den Stammdaten der Mappingtabelle `src/media/Mappingtabellen_NeTEx_v2.0.xlsx`, gekennzeichnet mit Blatt, Zeile und Guide-Stand. Der Code wird nie ersetzt.<br>(3) Ohne Stammdaten (z. B. allgemeine NeTEx-Werte wie `outbound`, `planned`, `alias`) nur der Code mit Vermerk „keine Erläuterung in den Stammdaten“. Keine eigenen Erläuterungen, keine XSD-Dokumentation (nur 9 % der Aufzählungswerte dokumentiert, oft unbrauchbar). |
| 30.10.2026 | Mappingtabelle auslesen | Beim Guide-Update liest ein kleines Skript die benötigten Blätter (`VMArt->NeTEx`, `Angebote`, `Facilities_gemappt`, `StopPlaceType`, `QuayType`, `StopUse`, `LineType`, `Weightening`) in eine JSON-Datei beim jeweiligen Guide-Stand. Pro Blatt definiert eine kurze Konfiguration die benötigten Spalten **über ihre Namen**; die Kopfzeile wird darüber gefunden, nicht über eine Zeilennummer. Fehlt eine Spalte, bricht `update-guide` mit klarer Meldung ab. Werte werden unverändert übernommen (auch Tippfehler/Schreibweisen der Tabelle). **Zellfarben (neu / nicht mehr verwendet) werden nicht ausgewertet:** für das Verstehen nicht nötig; mögliche spätere Ergänzung der Validierung. |
| 30.10.2026 | Eigene Dateien prüfen | Eigene Dateien lassen sich öffnen und validieren, lokal und in der Webversion (dort bleibt die Datei im Browser, kein Upload auf einen Server). Formate: eine XML-Datei, mehrere XML-Dateien oder ZIP (der Guide sieht Lieferungen als ZIP mit `NETWORK_OFFER`, `INTERCHANGE` usw. vor). Gleiche Validierung wie für Guide-Beispiele (siehe „Validierung mit Erklärung“). Ablauf: **zuerst Version erkennen, dann prüfen**. Passt die Datei nicht zum gewählten Guide-Stand (z. B. 1.10-Lieferung), zeigt das Tool das als Ergebnis und startet keine irreführende Prüfung; die Datei bleibt im generischen Explorer ansehbar. Webversion nur für kleinere Dateien. |
| 30.10.2026 | Mehrere Guide-Stände wählbar (vorbereitet) | `netexRealisationGuideSwitzerland.lock.json` enthält eine **Liste benannter Stände** (Name, Repo, Ref, Commit, XSD-Commit, Status wie „produktiv“/„in Entwicklung“), vorerst mit einem Eintrag („2.0 Entwicklung“, `next`). **Später**, wenn eine Produktivversion neben der Entwicklungsversion existiert: zweiten Eintrag ergänzen und Auswahl in der Oberfläche; Prüfung, Fahrtansicht und Stammdaten beziehen sich auf den gewählten Stand. Einschränkung: Für Versionen ohne maschinenlesbare Artefakte (z. B. Profil 1.0, nur PDF) ist nur eine XSD-Prüfung gegen die passende NeTEx-Version möglich; das Tool zeigt das an, statt eine vollständige Profilprüfung vorzutäuschen. |
| 30.10.2026 | Lieferdaten und LLM | Grosse Lieferungen nicht an das LLM senden; nur lokal per Skript auswerten. Siehe Arbeitsregeln in [CLAUDE.md](../CLAUDE.md). |
